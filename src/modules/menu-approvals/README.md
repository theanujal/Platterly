# menu-approvals

Owning chunk: Chunk 11 — Menu Selection, Approval Workflow & Kitchen Handoff.

Built 2026-09-17 per AJ's redesign (see `dev plans/chunk-11-menu-selection-approval-kitchen.md`): no per-event link/token — the customer reaches this through Chunk 8's tenant-wide Public Menu Link, identified by phone number, with a brand-new Order + Event created on every submission (never mapped to an existing one, even for a repeat customer).

`menu-approval.ts`:
- `submitEventDetails` — Group 11.2's whole intake flow (find-or-create Customer by phone -> new Order -> its Event -> a MenuSelection auto-advanced to CUSTOMER_REVIEWING).
- The PRD §29 state machine (`VALID_TRANSITIONS`) + named transition wrappers, and `setMenuSelectionItems` (§30 versioning: snapshots into `MenuVersion`/`MenuVersionItem` once past the pre-approval statuses, mutates in place before that).
- `listMenuSelectionsForKitchen` — Group 11.5's Kitchen Dashboard listing, no separate data model.

Group 11.3's admin UI (built 2026-09-18) lived at `src/app/(app)/menu-approvals/`: the `/menu-approvals` queue (now kept only for a role that approves menus but cannot open Orders) and the `/menu-approvals/[id]` review (since Phase 4 a redirect to the order's Menu Approval tab; its component was removed in Phase 5). Gated on the existing `menus: ["approve"]` RBAC action (owner/admin only, same as `events: ["approve"]`'s existing pattern). Items are editable only in `KITCHEN_REVIEWING`/`KITCHEN_CHANGES_REQUESTED` — `KITCHEN_APPROVED` has no transition back to review in `VALID_TRANSITIONS`, so the only remaining admin action past approval is Lock. Group 11.5 (the actual Kitchen Dashboard — Pending/Preparing/Ready/Completed derived from locked menus) is still Pending.

## Chunk 12 (2026-09-25) — the public multi-step order flow

`storefront-draft.ts` is the server side of `/{slug}` → `/{slug}/plan/{draftId}`: `startDraft` saves the visitor as a Lead (Customer, `leadSource STOREFRONT`, marketing consent recorded) and opens a `StorefrontDraft`; `saveDraftDetails/MenuChoice/Items/Venue` autosave each step with server-side validation; `buildDraftQuote` is the one pricing calculation (Review displays it, `submitDraft` books it); `submitDraft` atomically claims the draft, then creates Order → Event → MenuSelection (Customer-linked, straight to `KITCHEN_REVIEWING`). `listAbandonedOrders` powers `/abandoned-orders` (idle 30 min = abandoned; drafts purged after 90 days, lazily — no cron; the Lead stays). `storefront-selection.ts` (`splitPicks`) is the client-safe single definition of regular-vs-extra picks; `storefront-draft-constants.ts` holds the step list, thresholds and the consent default. `setMenuSelectionItems` now always stores quantity 1 and accepts an `isExtra` flag; `setCustomMenuPricePerPlate` lets the kitchen quote a Custom Menu. `submitEventDetails` (above) is legacy — kept only as a fixture for the state-machine tests.

**Several meals on the public form (2026-10-12).** A draft holds one set of picks per meal (`DraftData.meals[mealType]` = menu choice, dishes, add-ons); the wizard builds one meal at a time (`?step=menu&meal=LUNCH`, Continue goes to the next meal that is not done, then the Review). `saveDraftMenuChoice` / `saveDraftItems` / `saveDraftAddOns` take an optional `mealType` (none = every meal, the old single-menu behaviour). One guest number covers the whole order; `buildDraftQuote` prices each meal on its own menu (`perMeal`) and charges kids once, on the first meal's menu, as the Order does. `submitDraft` makes one meal-plan entry per meal (own Menu and price), a Multi Order when there are several, and mirrors the flat selection rows from the meal plan. A Custom Menu meal next to fixed-menu meals is quoted by the kitchen for the custom meal only. Drafts saved earlier are converted on read (their one set of picks stands for every meal). Multi-day events are still postponed.

**Edit in place and guest wording (2026-10-14).** On Build Your Menu, Event Summary > Edit opens `EventDetailsForm` in a side panel and saves through `saveDraftDetails`, so unsaved picks stay on screen. That function still clears every meal's menu and dish picks (keeping add-ons) when the event type or veg/non-veg preference changes; the other details keep them. The Event Summary lists Adult Guests, Kids (0–5), Kids (5–10) and Total Guests as separate rows (kids are counted on top of adults); `guest-summary.ts` writes the live total on the public form.

## Concurrency (Phase 0 of the Menu Approvals + Orders merge, 2026-10-16)

Every change to an approval's status is one database transaction under a row lock on its `MenuSelection` (`lockMenuSelection`): `transitionInTransaction` (all named transitions), `sendMenuForApproval`, `recallMenuFromCustomer` and `changeStatusManually`. The status is read again after the lock and the write is conditional on it, so two requests from the same old status cannot both pass; the loser gets the usual "Cannot move…" error (or "already …, nothing was repeated" for a repeat). The status change, the status-history rows, the order sync, the audit entry and, for Approve & Send to Kitchen, the Draft invoice are written together or not at all. Customer notifications and putting stock back after a cancel wait in an `afterCommit` list (`runHandoffTransaction`) until the transaction has committed. `generateInvoiceFromOrder` locks the order's row, so there is at most one live invoice per order whichever request creates it; an invoice failure inside a hand-off rolls the whole hand-off back (`KitchenHandoffError`, audited as `invoice.auto_create_failed`). No schema change was needed. Tests: `approval-concurrency.test.ts`.

**Also covered (2026-10-16, second round).** The first send for an order with no Event or MenuSelection: `ensureMenuSelection` and `syncOrderEvent` check and create under the order's row lock (`lockOrderRow`) in one transaction (`createEvent`, `createEventForOrder` and `createMenuSelection` take the transaction), so there is one Event and one MenuSelection; a later request waits and finds them, and a failure part way (for example no Event Type) leaves no Event behind. `setKitchenProductionStatus` is one transaction under the menu's row lock with a conditional write, so two stage changes at once record each real change once and the Order's status history stays an unbroken chain. Tests: `first-send-and-kitchen-concurrency.test.ts`.

## Review components (Phase 1 of the Menu Approvals + Orders merge)

The review is built from reusable client components in `_components/review/` so the Order page can host the same review; it does, as the order's Menu Approval tab (Phase 2), and the old page now redirects there. Nothing about how the page behaves changed. `approval-format.ts` holds the pure helpers; `use-approval-controller.ts` holds the state and handlers; the `approval-*` and `custom-menu-price-card` files are the pieces (action bar, stage notices, version bar, planner, status card, notes, history and its dialog, pricing); `types.ts` has the shared types and `ReviewActions`. The components never import a server action: whoever places the review passes the actions in, and each action keeps its own `menus: approve` and location check on the server. `review-data.ts` (`loadMenuApprovalReviewData`, server-only) builds the review's data for a selection the caller has already authorised; it reads with the caller's business id and checks no permission itself. The page (`app/(app)/menu-approvals/[id]/page.tsx`) still does `requirePermission`, `getMenuSelection` and the location check before calling it. Plan and decisions: `docs/menu-approvals-orders-merge-plan.md`. Tests: `__tests__/review-format.test.ts`, `__tests__/review-data.test.ts`, `e2e/menu-approval-review.spec.ts` (with `REVIEW_SNAPSHOT_DIR` set it also dumps masked page HTML and screenshots per state, for comparing a refactor against a baseline).

## Order Details integration (Phase 2 of the Menu Approvals + Orders merge)

The order page now has a **Menu Approval** tab built from the Phase 1 components and the same eight server actions (`orders/[id]/_components/order-menu-approval-tab.tsx`, actions handed in through `app/(app)/menu-approvals/_components/review-actions.ts`). `?tab=approval` opens it and `?tab=approval&version=N` shows a frozen version. `page-access.ts` holds the pure rules: `orderPageMode` (editable page, restricted approval-only view, or 403), `approvalCapabilities` (`canAct` = `menus: approve`; `canQuotePrice` = `menus: approve` and `orders: edit`), the tab ids and the not-started state. The restricted view (`approval-only-order-view.tsx`) is its own server-rendered view for `menus: approve` without `orders: edit`: it reads only the order summary, the status history and the approval, never payments, expenses, staffing, inventory, notes or the customer's phone and email.

Server rules added in Phase 2 (all under the menu's row lock, in one transaction each):
- **Price freeze** (`orders/price-freeze.ts`, `updateOrderInTransaction` in `orders/order.ts`): while the menu is Awaiting Customer Approval, Customer Reviewing, Customer Approved or Sent to Kitchen, an ordinary order save that changes a price field (guest counts, discount, transport, other and custom charges, Individual Pricing, the children's rates and types under Individual children's pricing) is refused with nothing written; an unchanged value is not a change. The meal plan has its own rule (Needs Review and Changes Requested only). `saveOrderWithMeals` writes the order fields and the meals in one transaction, so a failing meal plan leaves the order fields as they were. `approval-stages.ts` holds the stage list both modules use.
- **Custom-menu quote** (`setCustomMenuPricePerPlate`): needs `menus: approve` and `orders: edit` (the action asks for both), only in Needs Review / Changes Requested, audited with the price and order total before and after. **Send** is refused for a custom menu until it has been quoted (the message is `CUSTOM_QUOTE_MISSING_MESSAGE` in `approval-link.ts`).
- **No status change in place of an approval** (`manual-status.ts`): a hand-made move forward to Customer Approved or to the kitchen is refused while the order's price differs from the version the customer last saw. The way to a new price stays Recall, edit, Send Updated, the customer approves.
- **Notes on a Completed order** are refused by `addNoteToOpenOrder` (`menu-approval.ts`), which reads the order's status in the same transaction, under the menu's lock, that writes the note. The team action and the customer link (`askAboutApprovedMenuViaLink`, which also refuses Cancelled) both use it. A Cancelled order still takes a team note (it carries the reason it was cancelled).
- **`startMenuApprovalAction`** creates the approval (Needs Review) for an order that has none, through `ensureOrderMenuSelection`; nothing is sent.

**Kitchen lock (AJ, 2026-10-16).** Once an order has reached the kitchen no ordinary workflow changes it. `isKitchenLocked` (`orders/order-lock.ts`) is true when the order is Sent to Kitchen or Completed, or any of its menu approvals is Final/Locked (so a stale order status can't open it). It is read inside the writing transaction, after the menu's row lock, by: `updateOrderInTransaction` (every order field, guests, charges, meals, status), `deleteOrder` (a Cancelled order that never reached the kitchen may still go), `setMenuSelectionItems`, `setCustomMenuPricePerPlate`, `updateMenuApprovalMealPlan`, `saveOrderWithMeals`, `updateEvent`/`deleteEvent` (an order's event), and the customer link's venue form and confirmation. A plain save can no longer write Sent to Kitchen or Completed, and the order actions drop the `status` field. Left open by design: payments and invoices, the kitchen's own stage changes, stock sending, expenses/staff/logistics (Completed-only guard), event kitchen/inventory cards.
**Manual move-back boundary** (`orders/kitchen-lock.ts`, `changeStatusManually`): from Final/Locked a manual change may close the order (Cancelled, Delivered) or hold it, but may not leave Final/Locked, leave Cancelled, or lower the stage once the kitchen has started. "Started" fails closed and is read from: the current stage (In Preparation, Ready, Delivered); the audit log (the approval ever held one of those stages, even if the stage was set back to Pending); and stock sent to the order (`stockDeductedAt` or any stock-out row). At Pending with none of these, the team's way back for a mistaken send stays. Limit: cooking that was never recorded in Platterly (no stage change, no stock sent) can't be seen. Tests: `__tests__/kitchen-lock.test.ts`.
**Locking strategy (one order for everything).** Row locks are always taken in this order, only the steps a transaction needs: (1) the order's menu approvals (`menu_selection`, `ORDER BY id`), (2) the order row, (3) inventory rows and batches (inside `consumeStock` / `restoreOrderStock`). `lockAndReadOrder(tx, org, orderId, { alsoLockOrder })` in `orders/kitchen-lock.ts` is the single entry point for stock and delete paths; the approval paths take step 1 with `lockMenuSelection`/`lockOrderSelections` and reach step 2 by writing the order. The lock state is read only after the locks are held. `sendOrderItems`, `returnOrderItem` and `returnAllOrderItems` (production.ts) now take steps 1 and 2 and re-check the order's status under them (a send needs Approved or Sent to Kitchen; a return needs an open order), so a stock send and a manual move-back or stage change queue behind each other. `deleteOrder` is one 20-second transaction: locks, eligibility, `returnAllOrderItemsInTransaction`, delete; a refusal or a failure rolls the returned stock back. The hand-off also refuses a menu whose order was deleted a moment earlier. Tests: `production/__tests__/kitchen-lock-concurrency.test.ts` (a holder transaction owns the locks, the two operations are queued behind it one after the other, so the lock queue decides the order; plus six all-at-once runs that fail on a deadlock).

With a menu approval in place the order form's own planner is read-only and shows the saved meals (the same stored data the tab edits). Tests: `price-freeze.test.ts`, `custom-price-and-reapproval.test.ts`, `phase2-actions.test.ts`, `page-access.test.ts`, `e2e/order-approval-tab.spec.ts`.
